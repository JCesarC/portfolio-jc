## Context

Some documents in a mortgage file are very large. Condominium regimes, deeds and similar scans often weigh 130 to 150 MB, and sometimes up to 200 MB. To upload them, advisors usually split them first with an online PDF tool, and even then the pieces could still weigh 85 MB or over 100 MB.

When an advisor downloaded a client's file, every document kept that weight. The pipeline already had a compression step, based on Ghostscript running in JavaScript, but it barely reduced these files.

## What I built

A compression service dedicated to heavy PDFs, separate from the general pipeline and focused only on that problem:

- **Tuned for legibility, not just size.** Compression is tuned to keep text, logos and signatures sharp, because every page still has to be read by the lender. The goal is a meaningful reduction, not the smallest possible file.
- **Background mode.** When a document is uploaded to a field configured as heavy, such as a deed or a condominium regime, the backend starts the compressor Lambda. It runs in the background and, when it finishes, calls a webhook that saves the S3 path of the compressed file.
- **On-demand mode.** If a download includes a heavy document that has not been compressed yet, the download pipeline runs the compressor right then, waits for the result and puts the compressed file in the package.

The compressor is one stage of a larger set of Lambda functions, each with a single job, that build the downloadable file:

- **Auto-fill** of lender forms with the applicant's data.
- **Merge and package** the client's documents into a single ZIP.
- **Secure delivery** through short-lived pre-signed S3 URLs, so nothing is exposed publicly.

## Key decisions

- **A dedicated compressor for heavy files.** Instead of pushing the general compressor further, I built a separate service only for the documents that need it, leaving the rest of the pipeline unchanged.
- **Legibility over maximum compression.** A smaller file is useless if a signature or a figure on a deed can no longer be read, so the settings favor quality and accept a less aggressive reduction.
- **Compress once, ahead of time.** Configuration marks which fields hold heavy documents, so compression starts on upload and the work happens once instead of on every download.
- **A fallback inside the download.** On-demand mode makes sure a package never goes out with a heavy file that was not compressed beforehand.

## Results

- **Heavy documents up to 40% smaller**, with text, logos and signatures still legible and results comparable to the online tools advisors already used.
- **Lighter client file downloads.** Packages that include deeds or condominium regimes use the compressed versions instead of the original files.
- **No extra step for the team.** Compression runs automatically, driven by field configuration, both on upload and during downloads.
